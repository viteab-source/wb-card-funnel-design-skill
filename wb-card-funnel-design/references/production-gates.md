# Production-гейты

Читайте при подготовке claim-реестра, финальных изображений и статуса `production-ready`. Гейты одинаковы для одежды, электроники, товаров для дома и других категорий; различаются только факты и активированные риски товара.

## Один источник истины

- `intake.json` — единственный реестр фактов и исходников товара. Факт содержит `id`, `statement`, `source`, `variant`, `status`; при необходимости — `scope` и `variant_scope`. Исходник содержит `id`, `file`, `role`, `variant`, `quality`, `rights_status`.
- `production-manifest.json` по [шаблону](../assets/production-manifest-template.json) хранит только целевой вариант, claims и ссылки слайдов на `fact_refs`/`asset_refs`. Не копируйте в него характеристики или пути исходников.
- `media-manifest.json` по [шаблону](../assets/media-manifest-template.json) хранит только технический профиль и финальные файлы, связанные с production-манифестом через `run_id` и ID слайдов.
- `visual-dna.json` по [шаблону](../assets/visual-dna-template.json) хранит товарный anchor и принятый визуальный язык. Он не заменяет `intake.json` и не является источником фактов.

`null` у варианта означает «вариант не установлен», а не «подходит всем». Общий факт или исходник отмечайте явно: `variant_scope: all_variants` и `variant: null`. Используйте это только когда источник действительно подтверждает всю линейку.

## Реестр claims

Заносите в `claims` каждое обещание, которое покупатель может считать свойством товара:

- `explicit` — текст, цифра, подпись, иконка с однозначной расшифровкой;
- `implied` — обещание сценой или символом: вода, огонь, лёд, дети, медицинский знак, дополнительный предмет как часть комплекта, несовместимое устройство рядом с товаром.

Для claim обязательны точный текст/смысл, `scope`, `fact_refs`, статус и применимый вариант. Если визуальный намёк не занесён в реестр, скрипт его не обнаружит.

Минимальная структура записей:

```json
{
  "target": {"variant": "точный вариант", "variant_scope": "single_variant"},
  "readiness_status": "concept-ready",
  "claims": [{
    "id": "claim-01",
    "kind": "explicit",
    "text": "видимый текст или точное описание намёка",
    "scope": "product",
    "variant": "точный вариант",
    "fact_refs": ["fact-01"],
    "status": "reviewed"
  }],
  "slides": [{
    "id": "cover",
    "role": "cover",
    "claim_refs": ["claim-01"],
    "asset_refs": ["photo-01"],
    "status": "reviewed"
  }]
}
```

Статусы claims и слайдов: `draft`, `reviewed`, `approved`. Для `draft-brief` достаточно `draft`; для `brief-ready`/`concept-ready` нужен минимум `reviewed`; для проверки `production-ready` — `approved`. Слайд без claims допустим, если он честно показывает товар без дополнительного обещания; финальный слайд всё равно должен ссылаться хотя бы на один собственный исходник.

Перед финальным статусом выполните:

```bash
python3 scripts/validate_claims.py --pretty intake.json production-manifest.json
```

Коды завершения: `0` — структурный гейт пройден, `1` — содержимое не прошло проверку, `2` — ошибка вызова или чтения JSON. Даже код `0` не доказывает истинность источника, достаточность формулировки или наличие прав.

## Технический preflight изображений

Перед запуском создайте датированный профиль из актуальных правил WB. Значения в шаблоне — внутренняя рабочая база, а не вечные требования площадки. Затем выполните:

```bash
python3 scripts/preflight_media.py media-manifest.json
```

Перед прогоном заполните общий `run_id`, оставьте безопасную относительную ссылку `production_manifest_file`, перечислите ровно те же ID слайдов и переведите пакет/файлы из `draft` в `ready` только после фактического экспорта.

Скрипт проверяет связь пакета, существование файлов, сигнатуру и заявленное расширение PNG/JPEG/WebP, читаемую структуру заголовков, размеры с учётом EXIF Orientation, соотношение сторон, вес, уникальность ID/порядка/пути и точные SHA-256-дубли. Политику точных дублей задавайте в профиле: `fail`, `warn` или `allow`.

Скрипт не выполняет полный decode JPEG/WebP, проверку ICC/визуального цвета, near-duplicate анализ, проверку прав, сходство товара с исходником или проверку актуальности правил WB. Коды завершения: `0` — технический гейт пройден, `1` — содержимое не прошло, `2` — ошибка вызова или чтения обязательного JSON.

## OCR видимого текста

До финального экспорта сохрани `ocr-text-plan.json` с тем же `run_id` и для каждого ID слайда перечисли точные ожидаемые строки и прямоугольники `box` в пикселях `[x0, y0, x1, y1]`. План обязан покрыть каждый файл из `media-manifest.json`. После экспорта выполни:

```bash
python3 scripts/validate_ocr.py RUN_DIR
```

На macOS скрипт использует Vision для русского и английского; нужны Python с PyObjC и Pillow. В другой среде возможен Tesseract при установленной модели `rus` и Pillow. Tesseract без калиброванной уверенности оставляет совпадение в `review`; отсутствие OCR даёт `blocked`. Коды: `0` — все строки распознаны Vision с достаточной уверенностью; `1` — есть `review` или `blocked`; `2` — ошибка плана, файлов или запуска. OCR не проверяет правдивость характеристик, незапланированные надписи и качество дизайна. Сомнительные строки сверяй по пикселям и записывай решение отдельно; `review` не превращай в автоматический `pass`.

## Ручные гейты

После автоматических проверок человек или агент с просмотром изображений обязан подтвердить:

1. товар, цвет, геометрия, маркировка и комплект совпадают с точным продаваемым вариантом;
2. весь видимый текст прочитан и совпадает с одобренными claims;
3. незадекларированных визуальных обещаний и ложной комплектации нет;
4. права на фото, шрифты, логотипы и графику реально проверены, а не только помечены полем;
5. мобильная миниатюра и безопасная обрезка просмотрены;
6. официальные правила WB перепроверены, ссылки и дата сохранены в `qa-checklist.json` по [шаблону](../assets/qa-checklist-template.json);
7. `visual-dna.json` заполнен: все слайды сохраняют товарный anchor, общую световую логику и типографику, но не повторяют одну и ту же композицию; `product-passport.md` и contact sheet подтверждают маркировку, ракурсы и отсутствие подмены SKU.

## Правило статуса

Автоматические отчёты присваивают только `claims_gate` и `media_gate`; они не публикуют и не назначают итоговый статус сами.

`production-ready` допустим только когда:

- claim-гейт прошёл для режима `production-ready`;
- media-гейт прошёл по актуальному датированному профилю;
- все ручные гейты отмечены `pass` в `qa-checklist.json` и прошли `validate_design_gate.py --phase delivery`;
- нет открытого блокера по точному варианту, правам или правилам WB.

Иначе сохраняйте фактический статус: `draft-brief`, `brief-ready` или `concept-ready`. Наличие готового PNG само по себе не означает `production-ready`.
